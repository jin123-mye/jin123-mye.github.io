토스 앱 안에서 바로 두는 체스. 앱인토스와 원스토어에 출시해 운영하고 있습니다.

문제
체스를 처음 배우는 사람이 부담 없이 AI와 둘 곳이 마땅치 않았습니다.
해결
Stockfish 엔진을 웹 워커로 돌려 난이도별 AI, 형세 막대, 힌트·무르기를 만들고, 같은 코드를 안드로이드로 감싸 원스토어에도 올렸습니다. 게임물 등급분류(GRAC)부터 스토어 심사까지 직접 진행했습니다.
어려웠던 점
토스 웹뷰마다 화면 높이가 달라 체스판이 잘리는 문제가 반복됐습니다. 스크린샷 눈대중 대신 getBoundingClientRect로 실측해 보드 크기를 빈 공간에 맞춰 계산하도록 바꿨고, 빌드 산출물(.ait) 안의 CSS를 직접 열어 반영 여부를 확인하는 습관을 만들었습니다.

02

음원 분석 · 머신러닝

리드시트

유튜브 링크나 음원을 넣으면 박자·코드·조·보컬 멜로디를 분석해 폰에서 보는 코드표와 오선보를 만들어 줍니다.

문제
교회 반주를 준비할 때 악보가 없는 곡이 많아 매번 귀로 따야 했습니다.
해결
Demucs로 악기를 분리하고, beat_this로 박·마디, BTC로 박별 코드 확률, torchcrepe로 보컬 음높이를 뽑아 16분음표 격자로 양자화했습니다. 결과는 ABC 악보로 바꿔 abcjs로 그리고, 조옮김·카포 추천·코드 직접 고치기를 붙였습니다. 4분짜리 곡이 약 55초에 끝납니다(M1 Pro).
어려웠던 점
곡 중간에 박이 2배·반으로 튀어 마디가 어긋났습니다. 박 단위를 시간상 다수 쪽으로 통일하고, 마디 위치를 Viterbi로 찾게 해 3/4↔4/4 전환과 조바꿈까지 표기했습니다. 정답 악보 2곡과 대조하며 표기 높이·박 단위를 고쳤습니다.

03

백엔드 · 캡스톤 팀 프로젝트

뮤직 큐레이터 API 서버

감정을 분석해 음악을 추천하는 웹앱에서, 프론트가 Gemini·YouTube를 직접 부르던 구조를 Spring Boot 서버로 옮겼습니다.

문제
API 키와 프롬프트가 브라우저 번들에 그대로 노출되고, 검증·후처리가 프론트에 흩어져 있었습니다.
해결
Gemini 호출 전부와 YouTube 호출 6곳을 서버로 옮겨 프론트에서 키를 완전히 제거하고, 프롬프트는 서버의 템플릿에 가뒀습니다. YouTube 할당량은 Caffeine 캐시로 아끼고, 기록·좋아요는 Firebase 토큰으로 인증한 뒤 MySQL(JPA)에 저장합니다.
검증
컨트롤러→서비스→리포지토리를 실제 HTTP 경로로 통과하는 통합 테스트를 작성했습니다.

04

웹사이트 · 운영 자동화

대전백석교회 홈페이지

다니는 교회의 홈페이지를 처음부터 만들어 운영합니다. 폰에서 보기 좋은 앱형 화면이 기본입니다.

문제
주일예배 라이브가 끝나도 사이트는 고정 시각(12:30)까지 "라이브 중"으로 남아 있었습니다.
해결
처음엔 Cloudflare 워커에서 유튜브 상태를 읽었지만 구글이 클라우드 IP를 막아(429) 실패했습니다. 그래서 라즈베리파이에 감시 서비스를 두고 상태 기계로 판정합니다 — live는 즉시, offline은 2번 연속 + 시작 시각 이후에만 게시해 일시 오류로 꺼지지 않게 했습니다. 결과는 Pages의 별도 브랜치에 live.json으로만 올립니다.
검증
방송 없는 주일·방송 있는 주일·차단·게시 실패 재시도·재시작 후 재게시를 자가시험으로 돌리고, 공지바는 8가지 데이터 변형(0개·7개·긴 제목·기간 경계)으로 확인한 뒤 배포했습니다.
